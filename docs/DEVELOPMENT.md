# Руководство разработчика

Документ описывает текущую реализацию GigaChat CLI. Рабочие правила находятся в [AGENTS.md](../AGENTS.md), пользовательские инструкции — в [README.md](../README.md).

## Стек и запуск

Проект использует Python 3.13+, Textual, `langchain-gigachat`, pytest, pytest-asyncio и Ruff. Зависимости и настройки инструментов определены в `pyproject.toml`, зафиксированные версии — в `uv.lock`.

Все команды ниже выполняются из корня репозитория:

```sh
uv sync --locked
uv run gigachat
uv run gigachat --help
uv run gigachat -p "Объясни назначение проекта"
uv run gigachat -p "Объясни назначение проекта" --output-format json
```

Без аргументов запускается TUI; аргументы обрабатывает CLI. Запрос к модели требует настройки API по README. Не помещайте ключ в исходники, команды в документации или отслеживаемые файлы. Не отключайте проверку TLS по умолчанию.

## Карта проекта

```text
src/gigachat_cli/
  __main__.py       выбор TUI или CLI
  main.py           приложение Textual
  cli.py            аргументы, stdin, форматы вывода и коды завершения
  screens/          экран чата
  widgets/          вводимые списки, баннер и строка состояния
  styles/           CSS экранов Textual
  handler/          обработчики команд чата
  utils/            вспомогательные функции
  core/             ядро без зависимости от Textual
    model.py         интеграция с моделью, поток ответов и контекст
    command.py      выполнение системных команд и текущая директория
    config.py       чтение и запись настроек
    file.py         автодополнение путей
    file_edit.py    проверка путей, снимки файлов, diff, применение и откат
    session.py      рабочая директория, операции чата и жизненный цикл задачи
    sessions.py     локальное хранилище истории диалогов
tests/              проверки ядра, CLI и TUI
.github/workflows/  тесты, публикация и зеркало
docs/               документация и изображения
```

История для модели и отображение диалога — разные состояния. TUI сохраняет завершённые обмены, историю ввода и контекст модели через `core/sessions.py` в SQLite. Хранилище разделяет диалоги по канонической папке запуска. Обновления транзакционны: конкурентная запись со старой ревизией сохраняется как отдельный диалог. CLI сценариев автоматизации продолжает работать без пользовательского хранилища диалогов.

`ChatSession` не зависит от Textual. Она связывает запросы, команды и файловые операции с рабочей директорией, хранит последнюю обратную правку и управляет запуском и отменой задачи. TUI и CLI читают поток ответов через сессию. Экран чата отвечает за ввод, предпросмотр, отображение истории и клавиши отмены. Форматирование stdout, stderr и коды завершения остаются в `cli.py`.

TUI по умолчанию использует `textual-ansi`, чтобы фон и цвета шли из палитры терминала. Каждый обмен отрисовывается отдельным Markdown-блоком. При генерации экран объединяет фрагменты и обновляет только текущий блок. Последняя порция выводится сразу после завершения или отмены.

## Правки файлов

`core/file_edit.py` проверяет путь, читает снимок, строит diff и повторно сравнивает байты перед записью. `GigaChatManager.propose_file_edit()` отправляет снимок и задание отдельным запросом и принимает JSON с полным новым текстом. Путь выбирает пользователь. Ответ модели содержит только содержимое файла.

`handler/file_edit.py` запрашивает предложение у сессии. Виджет `FileReview` показывает diff и кнопки в диалоге и возвращает решение пользователя. После подтверждения обработчик передаёт правку сессии для записи. Откат использует тот же предпросмотр и повторную проверку файла.

Для регрессий в проверке путей и записи используйте `tests/test_file_edit.py`. `tests/test_core.py` проверяет контракт с моделью на поддельном клиенте, а `tests/test_ui.py` проверяет подтверждение, отмену и откат.

## Стиль Python

Соблюдайте PEP 8 и существующее оформление затронутого модуля. Для новых публичных границ задавайте понятные типы аргументов и результата. Не меняйте форматирование всего файла ради локального исправления.

Не блокируйте цикл событий синхронным сетевым запросом или ожиданием процесса. У фоновых задач должны быть понятный владелец, обработка завершения и отмены. Ошибки показывайте через существующие механизмы, сохраняя частичный ответ.

Машинные форматы CLI не смешивайте с баннерами, цветными сообщениями и диагностикой. При изменениях проверяйте `text`, `json`, `stream-json`, stdout, stderr и коды возврата по реализации `cli.py` и тестам.

## Комментарии и docstring

- Язык — русский; идентификаторы, названия API и секций Google docstring сохраняются на английском.
- Комментарий объясняет причину, ограничение или неочевидный контракт. Не пересказывайте очевидную строку кода.
- Пишите законченные предложения с заглавной буквы и точкой. В русском тексте используйте тире «—», а не дефис вместо тире.
- Docstring оформляйте по PEP 257 в стиле Google: краткое описание, пустая строка, нужные пояснения и секции `Args:`, `Returns:`, `Raises:`. Добавляйте секции только при наличии полезной информации; не дублируйте очевидные типы.
- Документируйте побочные эффекты, владение задачами, изменение файлов и условия отмены, если они существенны для вызывающего кода.
- Для тестов docstring необязательны: поведение должно быть понятно из имени и проверок. Это соответствует исключению Ruff в `pyproject.toml`.
- Не оставляйте закомментированный старый код. Для TODO укажите конкретное ограничение и условие завершения, желательно ссылку на задачу.

## Проверки

Основные команды повторяют CI:

```sh
uv run --locked ruff check src tests
uv run --locked pytest
```

Для локальной итерации выбирайте затронутые модули:

```sh
uv run --locked pytest tests/test_core.py tests/test_file.py
uv run --locked pytest tests/test_cli.py tests/test_arguments.py
uv run --locked pytest tests/test_ui.py
```

`tests/conftest.py` изолирует домашнюю директорию и очищает переменные GigaChat перед импортом пакета. Сохраняйте эту изоляцию; для новых случаев используйте `tmp_path`, `monkeypatch` и поддельные потоки ответов. Не подставляйте реальные ключи ради прохождения тестов.

TUI проверяется headless через `App.run_test()` и Pilot. Для визуальных изменений дополнительно запустите приложение в терминале: проверьте 80×24, широкий экран, длинные пути, кириллицу, Markdown, фокус, списки, прокрутку и отмену. Указывайте, какие терминалы и ОС проверены фактически.

CI запускает Ruff и тесты на Linux, Windows и macOS с Python 3.13 и 3.14; Python 3.15 на Linux проверяется экспериментально и не блокирует релиз. Источник матрицы — `.github/workflows/test.yml`.

Перед коммитом:

```sh
git diff --check
git diff
git diff --cached
git status --short
```

Для изменений только документации достаточно проверить содержимое, относительные ссылки, команды по коду и отсутствие ошибок diff. Не заявляйте запуск тестов приложения, если он не выполнялся.

## Сборка и выпуск

```sh
uv build
```

Версия определяется `setuptools-scm` по Git-истории и тегам; для корректной релизной сборки нужна история с тегами. Не добавляйте ручную версию в `pyproject.toml` в обход этого механизма.

Публикация GitHub Release запускает `.github/workflows/python-publish.yml`: проверки, сборку и публикацию в PyPI, а также дублирование релиза на GitVerse. `.github/workflows/mirror-gitverse.yml` зеркалирует ветки и теги при отправке на GitHub. Push имеет внешние последствия; локальный коммит ничего не публикует.

Теги, публикация релиза и изменение удалённых веток выполняются по отдельному поручению. Перед выпуском обновите пользовательскую документацию и проверьте сценарии установки и совместимость CLI.
