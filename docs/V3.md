# Решения для версии 3.0.0

Это согласованные границы разработки, а не описание уже выпущенных возможностей. Ветка разработки — `next/3.0.0`; номер релиза закрепляется тегом при выпуске.

## Порядок работы

1. Исправить существующие проблемы и закрепить существенное поведение регрессионными проверками.
2. Добавить создание и редактирование файлов через предложения изменений с просмотром diff и применением пользователем.
3. Переработать интерфейс на Python и Textual после стабилизации поведения ядра и файловых операций.

По ходу этих этапов отделять логику модели, файлов, команд и сессий от экранов. Отдельный процесс и протокол обмена сейчас не являются обязательными.

## Проблемы, выявленные при просмотре кода

- Экран чата очищает предыдущий обмен при каждом новом сообщении.
- Большой баннер постоянно занимает место, перед чатом требуется пройти меню.
- Поле ввода однострочное; нужно продумать многострочный ввод и вставку кода.
- Обновление ответа принудительно прокручивает область в конец.
- Отмена заменяет отображаемый ответ сообщением об отмене; полученный текст должен оставаться доступным.
- Обработчики фокуса возвращают его полю ввода; при переработке проверить навигацию, выделение и копирование.
- Индикатор ожидания и ошибки требуют более понятных состояний и доступных действий.

Это исходные наблюдения, не результаты полного аудита. Перед исправлением подтвердить конкретный сценарий и его причину. История отображения входит в исправления, окончательное оформление — в этап интерфейса.

## Первый вариант работы с файлами

Модель предлагает создание или изменение файла. Пользователь видит diff и может применить либо отклонить предложение. Не должно быть скрытого применения изменений.

При реализации нужны проверка границ выбранного проекта, защита от перезаписи изменившегося исходника и возможность откатить применённую правку без потери последующих внешних изменений. Предложения, отказы, конфликты и ошибки применения должны быть различимы в интерфейсе. Содержание файлов и diff рассматривается как данные, а не разрешение выполнять команды.

Удаление, переименование, массовые операции и автоматический запуск проверок не входят автоматически в первоначальный объём. Их контракты определяются отдельно перед добавлением.

## Направление интерфейса

Компактный рабочий чат: непрерывная история, многострочный ввод, спокойная общая палитра, управление контекстом файлов, понятные состояния и меню команд. Баннер и вводные советы уместны в пустом состоянии. При чтении истории поток ответа не должен сбрасывать прокрутку.

Базовые сценарии проверки: десять последовательных обменов остаются доступны; отмена сохраняет частичный ответ; вставка кода не отправляет запрос неожиданно; экран читается в 80×24. Сочетания клавиш должны учитывать различия терминалов.

Сохранение и восстановление сессий предложено как дополнительная возможность; включение в обязательный объём требует отдельного решения.

## Отложенное направление: агентный цикл

Сохранить для будущего второй вариант: модель самостоятельно выполняет цикл «прочитать → предложить/внести изменения → запустить проверку → исправить результат». Пользователь выбрал начать с просмотра diff и применения правок; автономный цикл не реализовывать в рамках этого первого варианта.

Перед переходом к нему отдельно определить разрешения на операции и команды, пределы цикла, отмену, фиксацию результатов и восстановление после ошибки. Наличие команды `!` в чате само по себе не означает разрешение модели запускать её.

## Будущий перенос на Rust

Долгосрочное пожелание — перенос на Rust. Текущая работа остаётся на Python и Textual; промежуточный интерфейс на TypeScript не выбран. Чёткие границы ядра и интерфейса должны позволить переносить проверенное поведение позднее. Rust и транспорт между процессами не являются требованиями релиза 3.0.0.
