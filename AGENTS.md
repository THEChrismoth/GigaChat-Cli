# Руководство для агентов и участников проекта

GigaChat CLI — ассистент для разработчиков в терминале на Python и Textual. Развивайте существующий проект, сохраняя интерактивный режим и CLI для скриптов.

Правила действуют во всём репозитории. Технический источник — [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md). Планируемое поведение не считайте реализованным.

## 1. С чего начать

1. Прочитайте [README.md](README.md) и руководство разработчика.
2. Проверьте `git status`, текущую ветку, последние коммиты и diff. Сохраняйте чужие изменения, включайте в коммит только свои файлы.
3. Откройте определения используемых функций, затронутый код и его тесты. Подтверждайте причину проблемы по реализации.
4. Если работа связана с issue или PR, прочитайте доступное описание и обсуждения. Не отправляйте сообщения от имени пользователя без поручения.

## 2. Архитектура и границы изменений

- Точки входа — `src/gigachat_cli/__main__.py`, `main.py` и `cli.py`; экраны — `screens/`, компоненты — `widgets/`, стили — `styles/`, обработчики — `handler/`, ядро — `core/`, вспомогательные функции — `utils/`.
- Общие правила модели, файлов и конфигурации должны использоваться TUI и CLI. Не дублируйте их в виджетах.
- При развитии отделяйте ядро от Textual. Будущий перенос на Rust не требует сейчас отдельного процесса или переписывания проекта.
- Исправляйте причину в пределах задачи. Не добавляйте попутную массовую переработку и зависимости без необходимости.
- Сохраняйте контракты CLI: форматы вывода, стандартные потоки и коды завершения. Несовместимые изменения согласуйте и документируйте.

## 3. Код, комментарии и данные

- Комментарии и docstring пишите на русском по стандарту [руководства разработчика](docs/DEVELOPMENT.md#комментарии-и-docstring). Имена Python и поля машинного протокола — на английском.
- Не выводите ключи API, переменные с секретами и содержимое личной конфигурации в логи и отчёты. Не перезаписывайте окружение и настройки пользователя ради тестов.
- Для тестов используйте временные файлы и поддельные клиенты. Реальные запросы к API и изменение пользовательских файлов не нужны для обычной проверки.
- Отмена должна освобождать задачи и процессы, сохранять уже полученный результат и возвращать интерфейс в рабочее состояние.
- Новое изменение файлов реализуйте через предложение diff и явное применение пользователем. Проверяйте границы проекта и изменение исходного файла после чтения. Самостоятельный цикл редактирования и запуска проверок требует отдельного поручения.

## 4. Интерфейс и проверки

- Проверяйте реальный экран терминала: чтение истории, фокус, прокрутку, вставку текста, отмену и открытые списки. Headless-тест не заменяет визуальную проверку.
- Проверяйте размеры 80×24 и более широкий экран; при изменении адаптации — также узкий терминал. Учитывайте длинные пути, кириллицу, код и многострочную вставку.
- Не кодируйте состояние одним цветом. Используйте подписи, видимый фокус и общие цвета темы; проверяйте контраст.
- Для исправления ошибки добавляйте регрессионный тест, если он проверяет причину и наблюдаемое поведение. Не создавайте тесты, которые лишь повторяют реализацию.
- Запускайте подходящие проверки из [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md). Сообщайте только фактически выполненные проверки, отдельно отмечайте непроверенные ОС и реальные сервисы.
- Перед коммитом просмотрите `git diff`, `git diff --check`, staged diff и `git status`. Документационные изменения проверяйте на ссылки, команды и соответствие коду.

## 5. Ветки, коммиты и релизы

- Основная ветка — `master`, разработка 2.6 ведётся в `next/2.6`. Проверяйте рабочее дерево до переключения веток.
- Делайте небольшие содержательные коммиты. Заголовок — на русском с префиксом из истории: `UPDATE:`, `FIX:`, `REDESIGN:` по смыслу. При необходимости после пустой строки перечислите конкретные изменения.
- Не добавляйте вымышленные подписи и `Co-Authored-By`. Не переписывайте удалённую историю, не публикуйте ветку, не сливайте PR и не выпускайте релиз без соответствующего поручения.
- Версия вычисляется через `setuptools-scm`; изменение версии и тегов относится к выпуску релиза. Ветка разработки не означает выпуск 2.6.

## 6. Документация и завершение работы

- README описывает доступные пользователю возможности. Руководство разработчика — архитектуру, запуск, стандарты и проверки. AGENTS.md — рабочие правила.
- Обновляйте документы при изменении соответствующего поведения. Не представляйте планы как готовые функции и не дублируйте подробные инструкции в нескольких местах.
- Планы версий, отложенные идеи и отчёты ведите в чате. Не создавайте для них отдельные файлы в репозитории без прямой просьбы пользователя.
- Продолжайте разрешённую обратимую работу самостоятельно. Уточняйте обязательные недостающие данные и действия за пределами поручения, которые трудно отменить.
- В результате кратко сообщите изменения, выполненные проверки, ограничения и состояние коммитов или публикации.
